技术演进 ​

微前端不是一次发明出来的，而是被一个个具体问题推着演化。理解“为什么出现”，比记住“怎么配置”更重要。

时间线 ​

阶段方案解决的问题留下的问题
早期iframe彻底隔离，天然独立部署通信、路由、弹窗、体验
2015 前后路由分发按路径挂不同应用切换整页刷新，状态丢失
2016Web Components浏览器级组件封装生态工具链、跨框架细节

2019+Module Federation构建时模块共享，依赖去重构建耦合、部署顺序、共享版本
2020+micro-app类 Web Component 接入，改造成本低Shadow DOM 兼容细节、生态
2021+wujieiframe 执行 JS + Shadow DOM 渲染架构较重、调试心智负担

每一代的核心动机 ​

iframe：隔离的基线 ​

iframe 用浏览器进程/上下文级别的隔离，解决了“互不影响”。但它的代价是：

  • 子应用是独立文档，主应用无法直接操作其 DOM。
  • 通信只能靠 postMessage。
  • 路由、弹窗、加载态、高度自适应都要额外处理。
  • 性能上多一份文档开销。

即便如此，iframe 仍然是很多后台系统（尤其涉及第三方页面、强安全边界）的合理选择。

single-spa：把“应用”抽象成生命周期 ​

single-spa 的关键贡献，是把子应用抽象成 bootstrap / mount / unmount 三个生命周期，并由根应用根据路由调度。它让“不同框架的子应用”有了统一接入方式。

但它只解决“调度”，不解决“隔离”。子应用仍然共享 window 与 document。

qiankun：把隔离和加载补齐 ​

qiankun 在 single-spa 之上补了三件事：

  1. HTML Entry：子应用只需提供 URL，不需要在主应用里写 import。
  2. JS 沙箱：用 Proxy 拦截全局变量读写。
  3. 样式隔离：通过选择器前缀或 Shadow DOM 限定作用域。

这三件事让 qiankun 成为国内中后台最常见的选择之一。

Module Federation：换一条路 ​

前面几代都在“运行时加载页面”。Module Federation 直接共享模块：

  • 子应用暴露组件或函数，主应用 import 远程模块。
  • 依赖可以声明为 shared，避免重复加载。
  • 不需要 HTML Entry，不需要沙箱。

代价是构建耦合更强：远程模块的产物结构、共享依赖版本、部署顺序都需要约定。

micro-app 与 wujie：降低接入成本 ​

micro-app 用自定义标签 <micro-app> 接入，子应用几乎不用改生命周期；wujie 则把 JS 放进 iframe 执行、把 DOM 同步到 Shadow DOM，试图同时拿到“隔离”和“体验”。

演进不是替代 ​

这七种方案不是“后者淘汰前者”。它们各自适合不同场景：

text
强隔离、低改造           ←→           高体验、高集成
iframe   wujie   micro-app   qiankun   single-spa   Module Federation   Web Components
1
2
  • 老系统多、团队弱、上线风险高：优先 iframe 或 wujie。
  • 中后台、Vue/React 混合、需要沙箱：qiankun 或 micro-app。
  • 组件级共享、构建体系成熟：Module Federation。
  • 跨框架标准组件：Web Components。

一个判断原则 ​

越靠近“运行时加载页面”，接入成本越低、隔离越依赖框架；越靠近“构建时共享模块”，依赖越明确、构建耦合越强。

选型时先确定你要的是页面集成还是模块共享，再决定隔离强度。
