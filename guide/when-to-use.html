何时用，何时不用 ​

微前端是组织复杂度的解法，不是技术复杂度的解法。技术问题优先用技术解决：拆包、懒加载、缓存、Monorepo，往往比引入微前端便宜得多。

五个“该用”的信号 ​

1. 多团队独立发布 ​

两个以上团队维护同一产品，每次发布都要一起回归、一起排队。微前端可以把发布解耦。

2. 存在无法短期重写的老系统 ​

老系统用 jQuery、AngularJS 或旧版 Vue，重写成本高。微前端可以让它和新系统共存，逐步替换。

3. 技术栈差异是既定事实 ​

例如并购、历史遗留、不同业务线技术选型不同。强行统一会带来更大的迁移风险。

4. 单仓构建已经明显变慢 ​

构建时间、依赖冲突、发布影响面已经成为日常痛点。

5. 需要按业务域独立演进 ​

不同业务域迭代频率差异很大，例如交易高频、报表低频。独立部署能减少互相干扰。

四个“别用”的信号 ​

1. 只有一个团队、一个发布节奏 ​

此时微前端只会增加构建、部署、调试、监控的复杂度，收益接近于零。

2. 只是想复用组件 ​

用组件库或 Monorepo 即可。微前端不是复用工具。

3. 团队没有基建能力 ​

没有统一的 CI、监控、日志、网关，微前端会把问题放大：版本不一致、资源 404、样式冲突都更难排查。

4. 子应用之间需要高频共享状态 ​

如果两个模块每秒钟都在同步数据，说明它们本就不该拆开。强行拆分会制造大量通信代码。

四类常见反模式 ​

反模式表现后果
为拆而拆按页面数量均分给不同团队边界与业务不一致，联调成本更高
只集成不治理能加载就行，没有版本与监控上线后故障定位困难
共享过度子应用直接 import 主应用源码独立部署名存实亡
隔离缺失全局变量与样式随意覆盖一个子应用出错，全站受影响

一张判断清单 ​

在立项前，逐条回答：

  • [ ] 是否有两个以上团队需要独立发布？
  • [ ] 是否存在短期无法重写的老系统？
  • [ ] 是否已有统一网关、CI、监控？
  • [ ] 是否接受子应用独立技术栈带来的维护成本？
  • [ ] 是否能在 4 周内做出一个可回滚的试点？
  • [ ] 是否有明确的子应用边界与接口契约？
  • [ ] 是否准备好版本矩阵与灰度方案？

7 条中少于 4 条为“是”，建议先不引入微前端。

如果决定要做，先做试点 ​

推荐路径：

  1. 选一个边界清晰、影响面小的业务域。
  2. 保留主应用，接入一个子应用。
  3. 打通 CI、部署、监控、回滚。
  4. 运行一个迭代周期，收集问题。
  5. 再决定是否扩大范围。

不要一次性把核心交易链路全部微前端化。先从边缘业务开始，把基建跑顺。

成本要提前算 ​

成本项说明
基建基座、脚手架、CI、CDN、监控
规范路由、通信、样式、版本、发布
调试跨应用排查、日志关联、Source Map
组织边界划分、接口评审、值班机制

微前端的收益是组织效率，成本是工程复杂度。只有当前者明显大于后者，这笔账才算得过来。
