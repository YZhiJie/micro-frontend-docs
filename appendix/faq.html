FAQ ​

按提出问题的场景分组。每条都给出结论和对应章节，不展开长篇论证。

选型 ​

微前端和组件库、Monorepo 有什么区别？ ​

  • 组件库解决"代码复用"，运行时仍在同一个应用里。
  • Monorepo 解决"代码仓库管理"，构建产物仍可能一起发布。
  • 微前端解决"独立开发、独立部署、运行时组装"，是组织与交付问题，不是代码组织问题。

如果只是想把公共组件抽出来，用组件库或 Monorepo 就够了。参见微前端是什么。

团队只有 5 个人，需要微前端吗？ ​

多数情况下不需要。人数少时沟通成本低，拆分反而增加集成、联调、部署的复杂度。先把模块边界做清楚，等出现"发布互相阻塞"再考虑。

新项目应该选哪个方案？ ​

新项目优先考虑构建时集成（Module Federation）或组件级方案（Web Components）。只有需要强隔离的遗留系统共存时，才选 iframe / qiankun / wujie 这类运行时方案。参见选型决策树。

qiankun 和 micro-app、wujie 该怎么选？ ​

  • qiankun：生态最成熟，HTML Entry + 沙箱，适合中后台聚合；对 Vite、Vue 3 的现代构建需要额外处理。
  • micro-app：接入方式是自定义标签，改动小，支持 Vite / esmodule 子应用，适合想低成本接入的团队。
  • wujie：iframe 执行 JS + Shadow DOM 渲染，隔离与性能折中，适合需要强隔离又要保留 DOM 能力的场景。

三者都能解决 80% 的常见需求，差异主要在隔离强度、接入成本、生态与调试体验。

接入与运行 ​

子应用一定要支持跨域吗？ ​

运行时方案（qiankun、micro-app、wujie）通常需要主应用 fetch 子应用的 HTML 或资源，因此子应用静态服务必须返回 CORS 头。本地开发时 Vite 配置 server.cors: true 即可。

子应用用 Vite 能接入 qiankun 吗？ ​

可以，但要额外处理：

  1. 子应用打包成 UMD / 库模式，产出固定的入口 JS 与 CSS。
  2. 关闭代码分割，或使用 inlineDynamicImports。
  3. 入口 HTML 由子应用自己维护，引用固定产物名。

本项目示例就是把 Vite 子应用构建后以 preview 方式提供，供 qiankun 加载。

子应用一定要导出生命周期吗？ ​

  • single-spa / qiankun：是，必须导出 bootstrap、mount、unmount。
  • micro-app / wujie：多数情况下不需要改造成生命周期，按普通应用启动即可。
  • Module Federation：不需要，暴露的是模块，由宿主按需 import。

本地开发时子应用能独立启动吗？ ​

能，而且应该能。示例中每个子应用都通过环境变量判断是否处于微前端环境：

ts
const isMicro = Boolean((window as any).__POWERED_BY_QIANKUN__);
if (!isMicro) {
  // 独立挂载，方便单人开发与调试
}

样式与沙箱 ​

Shadow DOM 能解决所有样式冲突吗？ ​

不能。Shadow DOM 隔离的是选择器作用域，但以下情况仍会穿透或失效：

  • 全局 CSS 变量与继承属性仍会影响内部。
  • document.body 上的全局样式（如字体、背景）仍然作用。
  • 第三方组件往 document.head 注入样式时不受 Shadow DOM 约束。

qiankun 的 experimentalStyleIsolation 够用吗？ ​

它会给子应用样式加前缀选择器，能解决大部分"互相污染"，但对 !important、body、html 级规则效果有限。强隔离需求建议直接用 wujie 或 iframe。

JS 沙箱能完全隔离吗？ ​

不能。常见的 Proxy 沙箱拦截的是全局变量读写，仍存在逃逸路径（如闭包持有原生 window、document 引用）。沙箱的目标是"降低冲突概率"，不是安全边界。真正的安全隔离只有 iframe（跨域时）。

路由与通信 ​

主应用和子应用的路由谁来管？ ​

两种模式：

  • 主应用管路由：主应用根据 URL 决定激活哪个子应用（single-spa、qiankun、micro-app 的默认方式）。
  • 子应用自治：子应用内部有自己的路由，主应用只负责挂载容器（wujie、Module Federation 常见）。

混用时最容易出现"双路由打架"，建议明确一层为唯一事实来源。

刷新页面后子应用 404 怎么办？ ​

子应用的静态服务需要配置 history fallback，把所有未知路径回退到 index.html。Vite 的 preview 默认已支持；Nginx 需要 try_files $uri $uri/ /index.html;。

通信一定要用全局状态吗？ ​

不一定。按耦合度从低到高：

  1. CustomEvent / postMessage（事件总线，最松）
  2. 属性 / props 传值（父子明确）
  3. 全局状态（qiankun initGlobalState、micro-app setData、wujie bus）

优先用事件和 props，只有确实需要共享状态时才引入全局 store。参见通信机制。

构建与部署 ​

子应用独立部署后，主应用怎么知道新版本？ ​

两种做法：

  • 主应用存子应用清单：发布子应用时更新清单（JSON），主应用启动时拉取，可实现灰度与回滚。
  • 固定 URL + 缓存控制：子应用入口文件名带 hash 或查询参数，主应用不做版本感知。

生产环境建议第一种，配合 CDN 刷新。参见独立部署与灰度。

Module Federation 的 shared 为什么必须单例？ ​

Vue、React 这类框架在运行时依赖模块级单例状态。如果宿主与远程各自加载一份，会出现响应式系统、调度器、Context 不互通的问题。配置 shared: { vue: { singleton: true } } 让双方共用同一份实例。

为什么本地启动 MF 要先构建远程应用？ ​

远程应用需要产出 remoteEntry.js 才能被宿主消费。Vite 插件在 dev 模式下对远程支持有限，因此本项目的脚本先构建远程、用 preview 提供服务，再启动宿主开发服务器。参见Module Federation。

GitHub Pages 部署后资源 404？ ​

多数是 base 配置不对。项目站点地址是 https://<user>.github.io/<repo>/，因此构建时必须设置 base = "/<repo>/"。本项目通过 CI 注入 DEPLOY_BASE，本地开发保持 /。

排障 ​

子应用挂载后白屏，怎么定位？ ​

按顺序检查：

  1. 网络面板：入口 HTML、JS、CSS 是否 200。
  2. 控制台：是否有跨域、document 为空、路由冲突报错。
  3. 容器：挂载节点是否在主应用渲染前就存在。
  4. 生命周期：mount 是否真的被调用，返回值是否是 Promise。

更多条目见故障手册。

子应用卸载后事件监听还在，导致内存泄漏？ ​

在 unmount 中清理：移除 window / document 监听、清空定时器、取消未完成请求、销毁框架实例。微前端环境下"卸载"是高频操作，必须当成正式生命周期对待。
