工程化总览 ​

示例能跑，只证明“技术可行”。要上线，还要补齐：

主题解决的问题章节
部署独立发布、灰度、回滚独立部署与灰度
监控错误定位、告警、链路错误边界与监控
性能首屏、缓存、预加载性能优化
治理版本、契约、规范治理与安全
安全沙箱边界、CSP、供应链治理与安全

上线前的最低要求 ​

  • [ ] 每个子应用有独立仓库与独立流水线。
  • [ ] 子应用产物有版本号，可回滚。
  • [ ] 主应用能识别子应用版本并做兼容处理。
  • [ ] 关键错误能上报到统一平台。
  • [ ] 有 Source Map，能还原压缩代码。
  • [ ] 有一个可灰度、可开关的降级方案。
  • [ ] 有跨应用日志追踪 ID。

运行时加载型方案（qiankun、micro-app、wujie）通常只需要：

  • 主应用部署一次。
  • 子应用各自部署，主应用通过配置或接口拿到子应用 URL。

构建时共享型（Module Federation）需要额外保证：

  • remote 先部署可用。
  • remoteEntry 地址稳定。
  • 共享依赖版本兼容。

主应用不要承载业务逻辑，只保留：

  • 布局与导航。
  • 路由调度。
  • 登录与权限。
  • 全局错误处理。
  • 子应用注册表。

团队协作约定 ​

事项约定
路由前缀每个子应用固定前缀，禁止跨域占用
通信只通过约定的 props / 事件 / 全局状态
样式禁止全局选择器，必须加命名空间
构建统一 Node / 包管理器版本
发布子应用独立发版，主应用维护兼容矩阵
回滚每个子应用保留最近 N 个版本

先做减法 ​

工程化最容易过度设计。建议按顺序补：

  1. 能回滚。
  2. 能定位错误。
  3. 能灰度。
  4. 再谈性能优化与自动化治理。

没有回滚与监控的微前端，不建议上核心业务。
