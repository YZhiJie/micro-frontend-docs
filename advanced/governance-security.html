治理与安全 ​

微前端把“一个应用”拆成“多个独立部署的应用”，治理难度随之上升：版本、契约、权限、依赖都变成了跨团队问题。

治理的四个对象 ​

对象问题手段
版本主应用与子应用不兼容兼容矩阵、运行时校验
契约props / 事件 / 全局状态字段变更类型定义、契约测试
规范样式、路由、通信各自为政Lint、评审清单、脚手架
安全沙箱逃逸、CSP、依赖漏洞白名单、SRI、审计

版本治理 ​

语义化版本 ​

  • 主应用：major.minor.patch。
  • 子应用：独立版本，但声明兼容的主应用范围。
json
{
  "name": "@mf/order",
  "version": "1.4.2",
  "microFrontend": {
    "shell": ">=2.3.0 <3.0.0"

规范治理 ​

建议把以下内容写进脚手架与 Lint：

  • 禁止全局 CSS 选择器。
  • 禁止直接修改 window 上的公共对象。
  • 必须导出统一的生命周期或注册函数。
  • 必须上报 app 与 version。
  • 必须提供独立运行入口。

安全边界 ​

1. 沙箱不是安全沙箱 ​

qiankun / micro-app 的 Proxy 沙箱主要防“误污染”，不是防“恶意代码”。子应用仍然可以：

  • 访问同源接口。
  • 读取 localStorage。
  • 发起网络请求。

真正的安全边界要靠权限控制与代码可信，而不是前端沙箱。

2. 子应用白名单 ​

只允许加载白名单内的域名：

ts
const ALLOWED = new Set(["https://cdn.example.com"]);

function assertEntry(url: string) {
  const { origin } = new URL(url);
  if (!ALLOWED.has(origin)) throw new Error("非法子应用入口");
}

3. CSP ​

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com 'unsafe-eval';
  style-src 'self' 'unsafe-inline' https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  frame-src https://trusted.example.com;

  • wujie / iframe 需要 frame-src 白名单。

  integrity="sha384-..."

5. 依赖供应链 ​

  • 锁定依赖版本（pnpm-lock.yaml）。
  • 开启依赖漏洞扫描。
  • 禁止从非信任源加载脚本。
  • 定期升级框架与构建工具。

权限设计 ​

主应用负责登录与权限，子应用只消费结果：

ts
registerMicroApps([
  {
    name: "order",
    entry: ORDER_ENTRY,
    container: "#subapp",
    activeRule: "/order",
    props: {
      user: { id, name, roles },
      can: (action: string) => acl.has(action),
    },
  },
]);

评审清单 ​

  • [ ] 子应用入口在白名单内。
  • [ ] 版本兼容范围已声明。
  • [ ] 通信字段有共享类型。
  • [ ] 无全局样式与全局变量污染。
  • [ ] 错误上报包含 app、version、traceId。
  • [ ] 依赖漏洞扫描通过。
  • [ ] CSP 与沙箱策略已确认。
  • [ ] 有回滚与降级方案。

一张治理成熟度表 ​

阶段特征
L1能加载，靠人工约定
L2有版本清单与回滚
L3有监控、契约测试、灰度
L4有自动化治理、权限与安全审计

多数团队稳定在 L2-L3 即可，L4 适合大型组织。
