独立部署与灰度 ​

微前端的核心收益是“独立发布”。如果每次子应用上线都要重新构建主应用，收益就不成立。

独立部署的三种形态 ​

1. 运行时清单 ​

主应用启动时拉取一份子应用清单：

json
{
  "order": {
    "version": "1.4.2",
    "entry": "https://cdn.example.com/order/1.4.2/",
    "compatibleShell": ">=2.3.0"
  },
  "product": {
    "version": "0.9.8",
    "entry": "https://cdn.example.com/product/0.9.8/"
  }
}

2. 构建时注入 ​

主应用构建时读取环境变量：

ts
const ORDER_ENTRY = import.meta.env.VITE_ORDER_ENTRY;

适合子应用地址稳定的场景，但发版仍需重新构建主应用。

3. 网关前缀 ​

子应用部署在固定路径：

https://example.com/order/     → 订单子应用
https://example.com/product/   → 商品子应用

主应用入口固定，子应用在自己路径下独立发布。需要处理 HTML 的 base 与资源路径。

主应用启动时校验：

ts
function assertCompatible(app: string, version: string, range: string) {
  if (!satisfies(version, range)) {
    reportError(`子应用 ${app} 版本 ${version} 不兼容 ${range}`);
    return false;
  }
  return true;
}

灰度发布 ​

按用户灰度 ​

ts
function pickEntry(userId: string) {
  const bucket = hash(userId) % 100;
  return bucket < 10
    ? "https://cdn.example.com/order/1.5.0/"
    : "https://cdn.example.com/order/1.4.2/";
}

按环境灰度 ​

  • 测试环境全量新版本。
  • 预发环境小流量。
  • 生产先 1% → 10% → 50% → 100%。

回滚 ​

必须具备三条回滚路径：

  1. 清单回滚：把版本号改回上一个稳定版。
  2. CDN 回滚：保留最近 N 个版本的静态产物。
  3. 主应用回滚：主应用自身可回滚到上一个构建。

回滚演练要纳入发布流程，而不是等故障时才开始想。

Nginx 配置示例 ​

nginx
server {
  listen 80;
  server_name example.com;

  # 主应用
  location / {
    root /var/www/shell;
    try_files $uri $uri/ /index.html;
  }

  # 子应用静态资源
  location /order/ {
    alias /var/www/order/;
    try_files $uri $uri/ /order/index.html;
    add_header Access-Control-Allow-Origin *;
  }

  location /product/ {
    alias /var/www/product/;
    try_files $uri $uri/ /product/index.html;
    add_header Access-Control-Allow-Origin *;
  }
}

CI 示例 ​

yaml
name: deploy-order

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @mf/qk-order build

部署顺序与依赖 ​

方案顺序要求
iframe无，地址可配即可
single-spa子应用入口可用
qiankun子应用 HTML 与静态资源可用
micro-app同 qiankun
wujie同 qiankun
Module Federationremote 必须先于 host 可用

Module Federation 的部署要额外注意：

  • remoteEntry.js 地址稳定。
  • 新版本先部署，再切流量。
  • 共享依赖版本兼容。
