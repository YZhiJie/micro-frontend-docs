加载：三种形态 ​

1. 文档级加载（iframe） ​

浏览器直接创建新文档，天然完成 HTML、JS、CSS 的加载与执行。

2. HTML Entry（qiankun） ​

主应用 fetch 子应用 HTML，解析出脚本与样式，再手动执行。好处是子应用只需提供 URL。

3. 模块级加载（Module Federation、Web Components） ​

直接 import 远程模块或加载自定义元素脚本，不涉及页面 HTML。

隔离：没有免费的午餐 ​

实际选型时，要先明确“必须隔离什么”。例如后台系统通常最怕样式污染，而不是全局变量。

路由：谁拥有 URL ​

三种常见模式：

  1. 主应用拥有路由：qiankun、single-spa 通过 activeRule 匹配路径。
  2. 子应用拥有路由：micro-app 的 baseroute、qiankun 的 activeRule + 子应用 history。
  3. iframe 内独立路由：主应用无法直接控制，需要 URL 同步。

路由设计的关键是：刷新页面后，能否恢复到同一个子应用状态。

原则：

  • 能用事件就不用共享对象。
  • 跨 iframe 必须用 postMessage，并校验 origin。

治理：决定能不能上线 ​

Demo 与生产的差距，主要在治理：

  • 子应用版本与主应用兼容矩阵。
  • 灰度与回滚。
  • 错误上报与 Source Map。
  • 性能预算与缓存策略。
  • 安全边界与依赖审计。

从工程化总览开始。

怎么用这组原理 ​

读每个方案页时，带着五个问题去看：

  1. 它怎么加载子应用？
  2. 它隔离了什么，没隔离什么？
  3. 路由归谁管？
  4. 通信用什么机制？
  5. 生产上还需要补什么？

能答出这五题，就算真正理解了一个方案。
