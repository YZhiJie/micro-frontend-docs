迁移路线 ​

迁移的目标不是“一次拆完”，而是“每一步都可回滚、每一步都有收益”。

四种迁移策略 ​

1. 新老共存（推荐起点） ​

主应用保留，新功能用子应用接入：

text
/legacy/*  → 旧系统（iframe 或直接跳转）
/order/*   → 新订单子应用
1
2

优点：风险最低，老系统不动。

2. 路由分流 ​

按路由把流量切到新应用：

nginx
location /order/ {
  proxy_pass http://new-order/;
}
1
2
3

适合新应用已经能独立承接完整业务域的情况。

3. 页面级替换 ​

同一个页面里，部分模块先替换：

text
订单详情页（旧）
  ├── 订单头（新子应用）
  ├── 商品明细（旧）
  └── 操作日志（新子应用）
1
2
3
4

需要主应用具备组合能力，适合 qiankun / micro-app / Module Federation。

4. 组件级替换 ​

只替换 UI 组件，不改变页面归属。适合 Web Components 或 Module Federation。

迁移步骤 ​

第一步：盘点 ​

  • 业务域与页面清单。
  • 技术栈与依赖。
  • 流量与核心链路。
  • 团队边界与发布节奏。

第二步：切边界 ​

按业务域切，而不是按页面数量切。输出：

text
订单域：订单列表、详情、退款
商品域：商品管理、库存
公共域：登录、权限、布局
1
2
3

第三步：搭基座 ​

主应用只做四件事：

  1. 布局与导航。
  2. 路由调度。
  3. 登录与权限。
  4. 监控与降级。

第四步：接第一个子应用 ​

选择标准：

  • 边界清晰。
  • 流量中等。
  • 可回滚。
  • 团队愿意配合。

不要选核心交易主链路做第一个。

第五步：打通基建 ​

  • CI/CD。
  • 版本清单。
  • 监控与日志。
  • 灰度与回滚。
  • 契约与规范。

第六步：扩面 ​

每接一个子应用，复盘一次：

  • 加载耗时是否达标？
  • 是否有样式冲突？
  • 通信契约是否清晰？
  • 回滚是否演练过？

技术栈迁移示例 ​

Vue 2 老系统 → Vue 3 新系统 ​

text
主应用（Vue 3）
  ├── /legacy/* → Vue 2 子应用（qiankun 或 iframe）
  └── /order/*  → Vue 3 子应用
1
2
3

Vue 2 子应用只需导出生命周期，不需要重写。

jQuery 老系统 ​

  • iframe：改造成本最低。
  • qiankun：需要把 jQuery 页面包装成 HTML Entry，注意全局变量。
  • wujie：侵入较小。

多技术栈共存 ​

  • qiankun / micro-app：运行时挂载，框架无关。
  • Module Federation：组件级共享，需要构建体系支持。

数据与状态迁移 ​

数据迁移方式
登录态主应用统一管理，props 注入
用户信息主应用请求，子应用只读
权限主应用下发 can(action)
业务缓存各子应用独立，避免共享可变对象
全局配置配置中心或全局状态

不要在两个应用之间直接共享可变对象。共享数据要经过明确的接口。

回滚设计 ​

每个阶段都要能回滚：

阶段回滚方式
新子应用接入路由切回旧页面
版本升级清单改回旧版本
基座升级主应用回滚构建
灰度关闭开关

回滚要能在 5 分钟内完成，并且不需要重新构建。

迁移检查表 ​

  • [ ] 业务边界已确认，且有负责人。
  • [ ] 主应用只承担基座职责。
  • [ ] 子应用可独立运行、独立部署。
  • [ ] 通信契约有类型定义。
  • [ ] 样式与全局变量无污染。
  • [ ] 路由刷新可用。
  • [ ] 监控包含子应用维度。
  • [ ] 灰度与回滚已演练。
  • [ ] 老系统退出计划已明确。

常见失败原因 ​

原因表现对策
边界按页面切联调成本高按业务域重切
基座承载业务主应用越来越重业务下沉到子应用
只集成不治理上线后故障多先补监控与回滚
共享可变状态互相影响改为 props / 事件
没有退出计划新老长期并存设定老系统下线时间
