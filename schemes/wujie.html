06 wujie ​

学习目标 ​

  • 理解 wujie “JS 在 iframe、DOM 在主文档”的双层结构。
  • 用 startApp 接入子应用并保持存活。
  • 用 bus 做主应用与子应用的事件通信。

wujie 的核心思路：

  • JS 隔离交给 iframe（浏览器级）。
  • 渲染通过 Proxy 把子应用 DOM 同步到主文档的 Shadow DOM。
  • 因此子应用既“隔离”，又出现在主应用布局里。

运行 ​

bash
pnpm dev:wujie

function bus() {
  return (window as any).$wujie?.bus;
}

onMounted(() => {
  bus()?.$on?.("portal:notice", (value) => {
    notice.value = String(value?.text ?? "");
  });
});

function pick(order: Order) {
  bus()?.$emit?.("order:select", { id: order.id });

坑点 ​

1. 调试心智负担 ​

JS 在 iframe 中执行，控制台的上下文可能不在主窗口。排查时要注意：

  • 事件监听注册在哪个 window。
  • document 指向的是主文档还是 iframe 文档。
  • 断点可能落在 iframe 的执行上下文。

2. window.top 相关逻辑 ​

某些库会判断 window.top === window。wujie 已经做了大量兼容，但仍有少数库需要打补丁。

3. 弹窗与 Portal ​

和 Shadow DOM 方案一样，弹窗挂到 document.body 会跳出隔离容器。需要约定挂载点。

4. sync 的选择 ​

  • sync: true：iframe 地址与主应用同步，适合需要分享 URL 的场景。
  • sync: false：不同步，减少路由耦合。

示例选择 false，让主应用完全掌控路由。

5. 资源与性能 ​

iframe 与 Shadow DOM 双层结构比纯 DOM 方案更重。首屏与内存要纳入性能预算。

6. alive 的副作用 ​

alive: true 会保留子应用实例，切换回来更快，但内存占用更高，且需要手动清理不再使用的应用。

与其它方案的差异 ​

维度wujieqiankunmicro-app
JS 隔离iframeProxyProxy
样式隔离Shadow DOM前缀改写Shadow DOM
子应用改造最少生命周期 + UMD最少
调试较复杂中中
适用强隔离 + 内嵌中后台Vite 子应用

如果你的团队曾被“全局变量污染”坑过，wujie 的 iframe 沙箱会更有安全感；代价是调试与性能成本。

练习 ​

  1. 把 alive 改为 false，观察切换后子应用状态是否丢失。
  2. 开启 sync: true，观察地址栏变化。
  3. 在子应用中故意修改 window.foo，回到主应用检查是否被污染。
  4. 用 props 传入初始公告，替代首次 bus 广播。
