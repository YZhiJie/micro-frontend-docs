07 Module Federation ​

学习目标 ​

  • 用 @originjs/vite-plugin-federation 暴露与消费远程组件。
  • 理解 remoteEntry.js、exposes、shared 的作用。
  • 掌握“先构建 remote、再启动 host”的运行顺序。

与前面方案的差别：

  • 共享的是模块，不是页面。
  • 没有 HTML Entry，没有沙箱。
  • 子应用不是“被挂载”，而是“被 import”。

运行 ​

bash
pnpm dev:module-federation
1

脚本会：

  1. 构建 mf_order 与 mf_product。
  2. 启动两个 preview（5190 / 5191）。
  3. 等待 remoteEntry.js 可访问。
  4. 启动 host dev（5189）。

不能先启动 host：远程模块尚未构建时，import 会失败。

坑点 ​

1. 运行顺序 ​

host 依赖 remote 的构建产物。顺序错误会出现：

text
Failed to load remote module
1

开发时用 scripts/dev-mf.mjs 自动等待就绪；生产环境要保证 remote 先部署，或做好降级。

2. 共享依赖版本 ​

shared: { vue: { singleton: true } } 要求 host 与 remote 的 Vue 版本兼容。版本差异过大可能导致：

  • 响应式失效。
  • 组件实例类型不匹配。
  • 运行时警告。

建议在 monorepo 中锁同一版本，或在 shared 中声明 requiredVersion。

3. CSS 处理 ​

Module Federation 共享的是 JS 模块，CSS 需要额外注意：

ts
build: {
  cssCodeSplit: false,
}
1
2
3

Vite 插件会把样式注入到模块加载过程中。如果远程组件样式丢失，优先检查 CSS 产物与 cssCodeSplit。

4. 部署与 CORS ​

远程模块通常部署在 CDN 或独立域名，需要：

  • 正确的 Access-Control-Allow-Origin。
  • 稳定的 remoteEntry.js URL。
  • 版本化路径，避免缓存串版。

5. 缓存与灰度 ​

remoteEntry.js 是入口，必须短缓存或加版本号；具体 chunk 可以长缓存。灰度时按用户切 remoteEntry 地址。

6. 不是页面级方案 ​

Module Federation 不适合直接迁移整页应用，除非子应用已经把页面拆成可复用组件。它更像“跨应用的组件/模块共享协议”。

练习 ​

  1. 把商品组件改成 React，观察 host 是否需要额外适配。
  2. 去掉 shared.vue，观察打包体积与运行时行为。
  3. 给 remoteEntry.js 加版本路径，模拟灰度发布。
  4. 故意让 5190 不可用，观察 host 的错误兜底。
